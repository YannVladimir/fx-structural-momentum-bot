# fx-structural-momentum-bot

**This is a EURUSD research / strategy-screening codebase, not a deployed trading bot.** Despite the repo name, there is no Expert Advisor (EA), no live or demo order placement, and no automated execution anywhere in this code. Every script here either downloads/audits historical market data or runs an offline, historical backtest/structural study. Read the [Status and findings so far](#status-and-findings-so-far) section before assuming any of this is ready to trade with.

## What this actually does

The code investigates whether a few simple, pre-declared EURUSD strategies have a historical statistical edge, using [MetaTrader5](https://www.mql5.com/en/docs/python_metatrader5) (MT5) as the only data source. Two independent research tracks are covered:

1. **Independent price-action screens** (`C_initial_research.py`, `C_price_behavior.py`, `C_sequential_tick_models.py`): three mechanical H1 candle models —
   - `momentum_12` — sign of the 12-bar price change,
   - `range_breakout_20` — close breaking outside the preceding 20-bar range,
   - `failed_breakout_20` — a one-sided breakout that closes back inside the preceding 20-bar range,

   each tested long and short with an ATR-based stop, a 2R target, and a 24-bar time exit, first on OHLC bars and then replayed against real historical tick data for an execution-accurate result.

2. **CRT + Supply/Demand structural study** (`C_crt_sd_structural_01.py`): a discretionary-inspired "Candle Range Theory" sweep/reversal pattern combined with a Supply/Demand zone and higher-timeframe bias filter, evaluated as a structural (does price reach a target level before an invalidation level) rather than a P&L question.

Everything is split into fixed TRAIN / VALIDATION / OOS (out-of-sample) date ranges that are declared once and never adjusted to chase a result; OOS has deliberately never been evaluated. See `EURUSD_research/C_RESEARCH_PLAN.md` and `C_RESEARCH_LEDGER.md` for the exact methodology and rules the research follows (no parameter re-tuning after seeing results, no silent exclusion of losing trades, bootstrap-based uncertainty estimates, etc).

## Status and findings so far

**No strategy here has been accepted as having a trading edge.** Per `EURUSD_research/C_RESEARCH_LEDGER.md`:

- All three mechanical H1 models (`momentum_12`, `range_breakout_20`, `failed_breakout_20`) were **negative in both TRAIN and VALIDATION**, both on OHLC bars and on the independently validated tick-execution replay, and remained negative under cost-stress scenarios.
- The CRT + Supply/Demand structural comparisons were **INCONCLUSIVE** due to small sample size, especially in VALIDATION.
- Broker commission and swap for the intended account have never been verified; several cost assumptions in the negative results are placeholders, not confirmed broker tariffs.

This does **not** prove EURUSD has no tradable edge — it means these specific, pre-declared hypotheses did not show one under the tested assumptions. Read the markdown reports in `EURUSD_research/` (especially `C_RESEARCH_LEDGER.md`) before drawing any conclusion from the code or the JSON result files.

## Tech stack

- Python 3.12 (should also run on 3.11)
- [NumPy](https://numpy.org/) for all numerical work (candle arrays, tick arrays, vectorized signal/statistics code)
- [MetaTrader5](https://pypi.org/project/MetaTrader5/) Python package for historical market data — **Windows-only**, and only required for the data-acquisition/audit scripts (see below)
- `unittest`-style tests, run with `pytest`

## Repository layout

```
EURUSD_research/
  C_RESEARCH_PLAN.md, C_RESEARCH_LEDGER.md        research rules, constraints, running decision log
  C_*_FINDINGS.md, C_*_REPORT.md, C_*_RESULTS.md   human-readable result reports (generated by the C_report_*.py scripts)

  # Data acquisition & auditing (require a running, logged-in MT5 terminal)
  C_data_audit.py                 symbol/account properties, H4/D1 download, OHLC sanity checks
  C_cost_coverage_audit.py        spread/cost probes on fixed historical days, deal-cost history
  C_download_continuous_ticks.py  resumable daily tick download for the TRAIN/VALIDATION window
  C_continuous_coverage_check.py  reconciles downloaded ticks against reference H1 bars
  C_boundary_investigation.py     investigates end-of-day tick/candle discrepancies
  C_probe_tick_boundaries.py      targeted re-download around those discrepancies
  C_repair_tick_boundaries.py     builds a corrected tick archive ("_02") fixing boundary gaps
  C_reconstruct_intraday.py       rebuilds M1/M5 bars directly from tick samples

  # Core, independently testable modules (no MT5 import, no network/data-file access at import time)
  C_tick_execution.py             tick-level trade execution/replay engine (market/stop/limit fill logic)
  C_crt_sd_structural_01.py       CRT sweep/reversal detector, Supply/Demand zones, statistical comparison helpers

  # Backtests / studies (require local historical data files, see below)
  C_initial_research.py           OHLC-only screen of the three mechanical models
  C_price_behavior.py             gross price-behavior diagnostics (no strategy, no R-multiples)
  C_sequential_tick_models.py     full tick-replayed backtest of the three mechanical models
  C_replay_smoke_check.py         smoke-tests the execution engine against 6 real pilot trades
  C_report_sequential_ticks.py    consistency checks + markdown report for the tick backtest
  C_report_crt_sd_01.py           markdown report generator for the CRT/Supply-Demand study

  # Tests (pytest; run without MT5, network access, or real market data)
  C_test_tick_execution.py        unit tests for the execution engine
  C_test_crt_sd_01.py             unit tests for CRT/SD timing and zone-freshness logic
  C_test_classify.py              unit tests for the CRT/SD statistics/classification helpers

conftest.py        creates a non-sensitive test fixture for the TRAIN/VALIDATION/OOS split dates (see Testing)
pytest.ini          pytest configuration (custom test-file naming pattern)
```

`raw_data/`, `CRT_research/`, and `archive/` are **intentionally not committed** (see `.gitignore`) — they hold large local tick/candle archives and a split-boundaries config file that are specific to one person's MT5 terminal and account, not shared source. Only the scripts, the two reusable pure-logic modules, their tests, and the generated markdown/JSON reports are version-controlled.

## Setup

```bash
python -m venv .venv
. .venv/Scripts/activate   # Windows
# source .venv/bin/activate  # macOS/Linux (data scripts still need Windows/MT5, tests do not)

pip install -r requirements-dev.txt   # numpy + MetaTrader5 (Windows only) + pytest
```

No API keys, tokens, or account credentials are hardcoded anywhere in this repo, and none are required as environment variables either: the `MetaTrader5` Python package talks to an **already running, already logged-in** MT5 terminal on the same machine (`MetaTrader5.initialize()`), so authentication is handled entirely by the terminal application, not by this code. There is therefore no `.env.example` in this repo — if you add any script that needs a broker API key, data-provider token, or similar, add it as an environment variable and put a placeholder in a new `.env.example`, never hardcode it.

To actually run the data-acquisition/audit/backtest scripts you additionally need:
- Windows, with the MT5 terminal installed and logged into a broker account that has EURUSD history,
- the local-only `raw_data/` and `CRT_research/data/Claude_split_boundaries_EURUSD.json` files these scripts expect (not included in this repo).

## Testing

```bash
pip install -r requirements-dev.txt
pytest
```

All 29 tests pass and run on any OS, with no MT5 terminal, network access, or real market data — they exercise only the two pure-logic modules (`C_tick_execution.py`, `C_crt_sd_structural_01.py`) against small, synthetic, inline fixture data.

`conftest.py` creates one small non-sensitive JSON fixture (the TRAIN/VALIDATION/OOS split boundary dates, already published in `C_EURUSD_CRT_SD_FROZEN_01.md`) at the local-only path `CRT_research/data/Claude_split_boundaries_EURUSD.json` if it isn't already present, purely so importing `C_crt_sd_structural_01.py` doesn't fail on a fresh checkout. It never overwrites a real local copy of that file.

`pytest.ini` sets a custom `python_files` pattern because the test files in this repo follow a `C_test_*.py` naming convention rather than pytest's default `test_*.py` — without it, `pytest` silently discovers zero tests.

### Bugs fixed during this cleanup

- `C_test_tick_execution.py`, `C_test_crt_sd_01.py`, `C_sequential_tick_models.py`, and `C_replay_smoke_check.py` imported modules named `Claude_tick_execution` / `Claude_crt_sd_structural_01`, which do not exist — the actual files are `C_tick_execution.py` / `C_crt_sd_structural_01.py` (apparently renamed at some point without updating the internal imports). This meant the existing test suite could never run (`ModuleNotFoundError`), silently, until this fix.
- Separately, `pytest` with no configuration discovers zero tests here at all, because of the `C_test_*.py` naming convention above — `pytest.ini` fixes this.

No calculation, signal, stop/target, or cost logic was changed by this cleanup — only imports, test discovery, and test fixtures.

### Known issue (not fixed — flagged only)

The output file names and local data-directory names referenced throughout the `EURUSD_research/*.py` scripts still use a `Claude_` prefix (e.g. `Claude_sequential_tick_results.json`, `raw_data/Claude_EURUSD_20260930/`), while the script files themselves were renamed to a `C_` prefix. This is purely cosmetic (it doesn't affect correctness — all the scripts agree with each other on these names) but it is inconsistent and worth cleaning up deliberately in a future pass, ideally by whoever is actively using the local `raw_data/`/`CRT_research/` folders, since renaming output files touches filenames that local analysis notebooks/scripts outside this repo may depend on.

## CI

`.github/workflows/ci.yml` runs `pytest` on GitHub Actions (Ubuntu, Python 3.11 and 3.12) on every push/PR to `main`. It does not and cannot place trades, connect to a broker, or use real market data — only the synthetic-fixture unit tests above run in CI.

## Risk disclaimer

This is experimental research software, not financial advice, and not a working trading bot. All results produced so far are negative or inconclusive under the tested assumptions, and none of this has been validated against real broker execution, live spreads, swap, or commission. Do not connect any of this to a live or demo account expecting it to place trades — that functionality does not exist in this repo. Past backtested performance, even if it were positive, would not guarantee future results. Anyone extending this into a live system should independently re-verify costs, broker fill behavior, and risk sizing before risking real capital.
